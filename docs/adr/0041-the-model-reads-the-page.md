# ADR 0041: The model reads the page; scripts do not interpret it

Status: accepted (2026-10-02); fit, application answers and resume import added the same day; apply facts, failures without stand-ins and site learning added 2026-10-03; fit judged during the search, for every kept job, 2026-10-13. Amended by [ADR 0051](0051-the-app-fixes-what-it-can-and-does-not-ask.md): a line the fact check has not checked no longer waits for the person.

Partly supersedes ADR 0023: compact card scans are no longer an accelerator that saves jobs.

## Context

The second usability round found jobs saved with a logo's initials as the company ("CR" for Cresta), with a board's tag chips as the location, and with a "DE" country code read as Delaware. Each came from code that parsed page text by rules: the `scan_cards` tool saved repeated DOM cards without a model call, and its parsed company and location were also handed to the extractor as evidence. The first fixes added more rules on top (initials patterns, tag-chip class names, class-name reads on detail pages). The same pattern sits behind other findings: a keyword list read "privacy notice" as a notice period, and title words decided role matches.

The agent already sees the whole page. It can tell a logo from a company, a tag from a place, and Berlin's DE from Delaware's.

## Decision

- **Job details come from the model.** A search saves postings only through `extract_jobs`, where the model reads the page and returns each job's fields. The `scan_cards` tool and the in-page link scanner behind it are removed. The extractor gets the visible page text and the page's links; scripts no longer pass it guessed companies or places, and no rule rewrites what it returned (initials, tag text, country codes). It returns a posting's own page as `canonicalUrl` and its apply link as `applicationUrl`, never one for the other. Because saved jobs' full listings are read and judged after the search, the agent saves from results pages and opens a posting only when its card cannot tell whether it fits.
- **Data published for machines is read as published.** JSON-LD `JobPosting` records and provider job-board APIs are the site's own structured data, not guesses, and stay deterministic. Page text is never parsed by rules to fill job fields.
- **Listing pages without a record are read by the model.** A listing that publishes no JSON-LD record is turned into plain text and the model returns the posting, or nothing when the page is not one (a sign-in page, a talent pool, a closed listing). Page text is no longer cut, trimmed or accepted by word counts and cue words.
- **The model decides fit.** While a search runs, the model judges every job it keeps in batches of twenty as the jobs land, so scores appear during a long search: role, preference and place fit, a score, a recommendation, reasons and gaps. After the search it judges again only what changed (a listing read in full) and the plan's older jobs that need a new verdict. "Read and assess listing" asks it about one listing in full. Its verdict is stored on the assessment and stands: no rule recomputes the score, caps it, or corrects the place. The rule scorer (role families, title words, seniority from titles, country tables, requirement regexes) is removed; a job the model has not judged yet says "Not judged yet" and shows no number, and a job is judged again when the profile, the goals or the listing change. What stays in code is arithmetic: salary against the saved minimum, the application path's effort, and counts of the requirements the model listed.
- **The model answers application questions.** The apply agent gets all of the person's facts (contact details, eligibility, saved answers, roles, education, the resume going out) and answers the form from them, a page at a time with `fill_fields`. What it types or chooses goes in when it is one of the person's stored values word for word (an email, a phone number, a link, a saved sentence), or the person's saved answer to that exact question, or the fact check (a model reading the answers against the person's facts, one call per batch) supports it. An unsupported answer is not entered and the model is told why. Without a fact check only stored values go in. No per-field rule picks an answer: the answer sourcing, work-country, phone-country and work-history rules are removed. A required field still empty after one reminder goes to the person with the form.
- **The model says which questions the person's permissions cover.** Once per form page the model classifies every question: whether it asks about the person's pay, and whether it is a declaration and which kind. The pay switch and declaration approvals act on that reading, in any wording or language. If the model cannot be asked, the keyword lists stand in, so a permission is never left unguarded.
- **The model decides what a search keeps and what is closed.** "Best matches only" drops a job only when the model judged its role, place or goals wrong or would skip it; a job it has not judged is kept. The model's verdict also says whether the listing itself is closed, quoting it; no phrase list closes a listing. The "this search returned only remote jobs" warning reads the model's place verdicts.
- **Code keeps safety and mechanics.** Final submit authority, consent, credentials, allowed origins, identity of the same URL, counts, dates and time zones, and file fingerprints stay deterministic. So do the person's own switches: pay they keep to themselves, declarations they did not approve, companies they blocked and places they excluded.
- **The model reads the resume.** Each import section (identity and contact, work history, background) is read by the model with the whole document available. A call that fails for a passing reason is asked again; a section still unread is named to the person and nothing is guessed for it. On the model path there is no regex pass, no rule-read candidate beside the model's, no rule fill-in of company and place, no regex split of title from employer, and no rule check of the model's values against the resume text; reconciliation keeps only structure (merging, de-duplication, the person's own edits and identity). Without any model (tests, or a build with no AI) the rule reader stands in, as before.
- **One model read per page.** The model reads a page once and returns everything on it, rather than being called per field or per job. Fit is judged many jobs per call, up to five calls at once (a call that fails is asked once more); a full assessment of one listing (about a minute) runs when the person asks for it. Agent runs shorten tool answers older than the last four, so each turn sends the current page rather than every page so far.
- **A failed model call is a failure, not a rule guess.** When the model cannot be asked, the person is told and what they had stays: page reads report the failure instead of "no jobs", import conflicts stay in setup review, the profile and resume assistants say nothing was changed, a resume the AI could not write leaves the job's resume as it was (a first attempt shows a retryable failure), and fit stays unjudged. No built-in parser, editor, extractor or resume writer answers in the model's place.
- **The model checks resume claims.** A tailored resume keeps the model's lines as written. Before a draft is validated and kept, the model checks each generated line against the person's evidence (profile, saved records, imported resume), many lines per call: supported, a stretch the person confirms, or unsupported. The verdicts are stored with the draft by the line's content hash and reused until the wording, the evidence or the tailoring strength changes; the Resume Assistant's proposals are checked the same way before they are offered. The writing agent repairs what the check flags before it can finish. When a generated resume is kept, any line the check still did not pass (and, outside aggressive tailoring, any stretch) gets the checker's own fix: rewritten to what the evidence backs, or hidden when nothing in it can be kept; the rewrites are checked once more, and a line that still fails waits for the person. A line the person wrote, a line that repeats their records or resume word for word, and a skill on their profile need no check. A generated line not checked yet waits for the person. No token-overlap classifier, listing-skill injection, job-text bleed detector or metric rule judges or removes lines any more.
- **The model's routes decide where a search or source check starts.** The kind the source check's review gave each route (listing, search, collection) stands over what its address looks like, and a source check's phases start from those recorded routes. No keyword is picked by rule and typed into a search address: the search agent uses the site's own search with the person's goals in front of it.
- **The model notes unfinished resume writing.** The fact check also says when a generated line is a keyword list, a fragment, filler or first-person prose, and gives a fix that a generated resume gets. No word rule drops a line or swaps a summary out, and the person's own lines get no note.
- **The model organizes what a source check learned.** The check's final review keeps, files and reconciles the check's notes and says whether a future search can rely on them; its lists and that call stand. No keyword list filters learned lines, scores their quality or decides when they are validated. Without the review the notes stay a draft and say so.

## Consequences

Searching a results page now costs one model call where the card scan cost none, and a search adds one judging call per twenty jobs it keeps, up to three at once beside the search (2026-10-13: the cap of five calls per run left most of a large search unjudged, so a 1,500-job search now judges all of them); with "Best matches only" or a result limit, that judging happens before the jobs are kept. A form page adds one call to classify its questions. Jobs saved before this change keep whatever the scan recorded until they are seen again. When the model is unavailable, jobs show "Not judged yet" and are judged on the next search; nothing pretends a rule guess is the model's.

Jobs scored before the scorer was removed show "Not judged yet" until a search finds them again or judges them as older jobs of its plan (at most a hundred older jobs per search). With a result limit set on a search plan, the model judges the new jobs before the limit picks, so the limit keeps the best fits; the verdicts are reused after the search. A resume that names someone other than the profile's owner adds nothing, jobs and schools included, until the person reviews it.

A form page is usually filled in one or two model turns plus one fact-check call, instead of a turn and a lookup per field. Required questions the model could not answer from the facts reach the person once, after a single reminder, rather than the run stalling on them.

What stays deterministic on purpose: the person's own lists (blocked companies matched by name, excluded places matched by their own words), the arithmetic of pay against a saved minimum, the cross-listing check that drops a pay band every listing of a site shares, the keyword fallback for pay and declaration questions when the model cannot be asked, and the label-to-option spelling match when a dropdown words the model's answer differently. Still rule-based: the base draft built from the profile when there is no model at all or the listing text was never captured.
