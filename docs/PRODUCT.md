# Product

`Nestor` is one local-first desktop app with two modules:

- `Job Finder`
- `Live Assistant`

## Shared Baseline

- shared local profile, documents, reusable answers, and application history
- shared browser runtime, source intelligence, AI provider roles, desktop shell, settings, tray, and hotkeys
- UI-first workflows with agent assistance inside bounded product surfaces

Eight consistency principles govern every Job Finder surface. They generalize
the defects real users reported, so a new screen is judged against the
principle, not against whether that exact case was reported before:

- **One component per job.** One tab style, one list-row style, one badge,
  chip, and count treatment, one card, one toolbar control height, one button
  hierarchy, one empty state, one dialog and close affordance. A second visual
  implementation of the same job is a defect, and a guard test pins the
  canonical one.
- **Nothing shifts.** Opening or closing a panel, selecting a row, hovering,
  loading, resizing, or a toast never moves or resizes unrelated content.
  Floating surfaces overlay; they never reflow. A skeleton is laid out block
  for block like the loaded screen.
- **Everything in reach.** At every supported size down to 1024x720, and in
  short windows, a screen's primary action is visible without scrolling.
  Floating surfaces stay inside the window and never cover the primary
  action, a tab strip, or a composer; popovers fit or scroll internally.
- **Aligned and even.** Controls in one row share one height, radius, and
  border token; groups align to one axis; the header is centred; gutters are
  identical across routes.
- **One fact, one voice.** A number or state shown on two screens uses the
  same noun and the same population. No raw error strings, identifiers, or
  internal vocabulary reach a user surface, and no label promises something
  the app cannot do.
- **Legible.** Text is at least 4.5:1 and boundaries and states at least 3:1 (an editable field's resting border is the one softened exception, held just above the inert panel band with a shadow and a lighter fill, while its hover and focus boundaries clear 3:1)
  in both themes; disabled looks disabled; links look like links.
- **Use the room.** No dropdown or disclosure hides what the space already
  shows; no empty columns; no oversized hero above a small next action.
- **Honest loading.** Every wait shows elapsed and expected time or a real
  progress signal, never a fabricated percentage, and loading states are laid
  out like the loaded state.
- one published type scale rather than a per-screen one: headings render at 24 / 19 / 16 / 14px for h1-h4, all semibold and strictly decreasing, so a subsection heading can never render larger or heavier than the section heading above it; text typed into any field renders at body size instead of inheriting its container's size; no label, chip, badge, or table header renders below 11px; and the page title is a fixed size, so it does not change between routes; an eyebrow or kicker label — the small uppercase word above a card's real title — is a styled non-heading element that names its region through `aria-labelledby`, never a heading tag, so the document outline a screen reader walks matches the visual hierarchy instead of announcing a 14px badge as a section heading
- one contrast and state floor: any control whose only boundary is a border clears the 3:1 non-text floor against both the panel and the page canvas in both themes (editable fields carry that floor on hover and focus; at rest they sit one step above the inert panel band, at about 2.7:1, with a shadow and a lighter fill, so they read as quiet wells rather than outlined boxes), a disabled control loses its fill rather than differing only by label colour, text-only controls are always underlined so hue is never the only signal that something is clickable, scrollbar thumbs are visible because on a clipped screen the scrollbar is often the only "there is more" cue, and attention states that are not failures carry their own warning tone instead of borrowing the failure hue
- one breakpoint-precedence rule in the renderer: Tailwind v4 emits arbitrary `min-[…]` / `max-[…]` media variants _before_ the named breakpoints (`sm: md: lg: xl: 2xl:`), so when the same element sets the same CSS property from both and both queries match, the named breakpoint wins on source order. An arbitrary variant that must beat a still-matching named breakpoint therefore has to be marked important — `min-[1440px]:!px-4`, not `min-[1440px]:px-4`. An unprefixed base utility needs no override, because Tailwind already emits it before every variant. `apps/desktop/src/renderer/src/tailwind-variant-order.test.ts` resolves the winning utility through that emission order and fails on a reintroduced plain variant
- one selection rule for every list: selecting a row in Find jobs, Shortlisted, or Applications changes only a background tint and an accent bar drawn inside the row, plus `aria-current`. Padding, margin, and border width are identical in both states and every content line keeps its slot, so a selection can never resize a row or move the rows below it

## Job Finder

Target authority model:

- Job Finder will support `prepare_only`, `confirm_before_submit`, and
  `autonomous_submit` modes under an explicit user-scoped authority envelope.
  Autonomous mode is a core product capability and may complete final submission
  when the saved policy covers the exact application and action. Unknown facts,
  security challenges, unavailable credentials, and actions outside the policy
  still pause rather than being guessed. See ADR 0012.
- Autonomous submission is implemented: `autonomous_submit` (Send for me) sends
  inside the saved envelope, `confirm_before_submit` sends on the person's Send
  press, and `prepare_only` never sends (ADR 0024, ADR 0027).

Current baseline:

- Users configure which job sources run; importing or suggesting a source does not enable it. Discovery, source-debug, and apply preparation improve through source-generic browser policy, typed evidence, and learned target instructions—not per-board adapters or rescue logic in shared product flow. Reusable provider adapters (for example public Ashby or Workday endpoints) normalize payloads only; see [ARCHITECTURE.md](ARCHITECTURE.md) and [ADR 0007](adr/0007-source-generic-browser-workflows.md).
- The normal user flow is numbered and sequential: (1) Profile, including first-use setup and resume evidence review; (2) Find jobs, which searches enabled sources using the saved profile and search settings; (3) Shortlisted, which reviews selected jobs and prepares optional tailored drafts; and (4) Applications, which shows each application in one of five states and sends it only under Send for me or on the person's Send press under Ask before sending. Needs you, Tasks, and Settings support this flow but are not extra steps in it.
- Job Finder navigation is the journey and nothing else: Home, Profile, Find jobs, Shortlisted, and Applications. Reference and configuration surfaces have no navigation entry of their own: `Settings` is pinned to the rail, Search plans and Companies open from workspace search, Safeguards opens from the Home or Find jobs link when a review waits, and Outcomes and Resume approaches open only from the page that needs them. At CSS widths of at least 1440px the persistent 17rem sidebar lists the journey in its scrolling list and pins `Settings` at the very bottom of the rail, outside that list and with no group label above it, with the `Keyboard shortcuts` reference as one small square control beside it (stacked above the gear on the collapsed rail), because Settings is not a step of the journey and should be found in the same place at every window height. The collapsed 4rem rail shows the same rows as icons with their tooltips. The sidebar owns its own vertical scrolling with the collapse toggle pinned above it, so a short window scrolls the destination list instead of clipping it. Below 1440px, where the top navigation genuinely has no room, the compact `More` menu holds `Settings` and the `Keyboard shortcuts` entry, with no introductory prose and no embedded shortcut table; its internal scroll region and upward flip are the short-window fallback rather than the normal case. `Needs you` and `Activity` stay in the header attention group at every width. The sidebar paints no group label at all: its one journey list carries the name `Your job search` for assistive technology only, and menu group labels elsewhere stay 11px eyebrows, never heading tags. Every destination count in the sidebar and the compact top navigation is the same quiet pill (soft fill, tabular figure) sitting at the row's trailing edge; on the collapsed rail it becomes a small marker at the icon's top-right corner, ringed in the rail colour so it never covers the glyph. Attention counts keep their filled primary pill with the noun. The keyboard-shortcut reference is its own dialog, opened with `?` or from that entry, one row per action with its scope sentence and the keycaps that fire under that scope. One alignment rule governs the header at every width: it is three regions — the wordmark on the leading edge, the module switcher centred, and search, `Activity`, `Browser`, and `Needs you` on the trailing edge. The switcher is the middle track of a grid whose two side tracks are always equal, so it sits on the window centre line rather than beside the wordmark, and it is never absolutely positioned over the native window controls. Each platform's native window-control inset is reserved inside its own side region — the macOS traffic-light reserve is mirrored on both edges of the brand row, and the Windows caption buttons this frameless window paints itself are reserved inside the trailing region — so reserving either one can never shift the centred switcher off that line and the attention group never sits under the caption buttons. Below 1440px the destination navigation card is centred on that same axis instead of beginning on the shell gutter: it still hugs its contents and neither wraps nor clips, and where the attention group shares that row its reserve stays one-sided so the card stays on one line at the 1024px minimum window and at native 125% zoom. The page content still begins on the shell gutter, and the compact navigation, the compact `More` trigger, and `Needs you` all mark the current destination with the sidebar's own filled surface, indicator bar, and bolder label rather than colour alone. Every route's page title sits at the same offset from the shell: routes add no top padding of their own above the page header, and the shell (or the locked-route layout, for routes that own their top edge) supplies it. The Settings section that decides what Apply does is named `Applying` and remains a Settings section rather than a destination: three modes that save the moment one is picked (the chosen mode is remembered, so later Apply and Apply to all journeys never revisit Settings), and the daily limit. Safeguards states the whole application boundary in one sentence and keeps every active application permission inspectable and revocable there. At CSS widths of at least 1440px the brand row spans the sidebar and content columns as one grid row that cannot wrap, so the centred module switcher stays on the header line — the same arrangement the compact layout uses — instead of wrapping out of the 3.5rem header and colliding with the page title; module labels never break mid-phrase. The compact `More` surface is bounded and so is its destination list: the list scrolls inside its own region with edge hints, so at short window heights it can never paint across the pinned `Keyboard shortcuts` footer, and every destination stays reachable by scroll and by arrow keys. In the shortcuts dialog a modifier and its key are separate keycaps joined by a muted, decorative `+` (⌘ + K); a literal-key shortcut such as `/` or `?` stays one keycap
- Every popover, menu, dropdown, and floating panel is placed by one shared rule rather than anchoring below its trigger unconditionally: it flips above the trigger when the space below cannot hold it, shifts back inside the window instead of clipping horizontally, derives its height from the space actually available rather than a fixed value, and exposes whatever does not fit through an internal scroll region whose `more above` / `more below` hints print at the edge they describe. No floating surface has content reachable only by resizing the window.
- Guided setup is five form-first steps: a compact horizontal stepper (Import, Basics, Work history, Job targets, Extras) sits under the page title, and the step's fields start in the first viewport. Extras is explicitly optional and skippable — it merges the former "Your story" and "Screener answers" steps — and the former "Ready check" step is gone: "Finish setup and find jobs" becomes the primary action on Job targets as soon as the required items are met, and stays available on Extras. Setup has one readiness system: the stepper chip carries each step's outstanding count, the step body lists those items, and the sticky footer states in words whether setup can finish and what is still needed. Continue buttons name the next step ("Save and continue to Work history"); only required setup items (a name with one contact method, one enabled source, and the two work-eligibility answers on Job targets, see [ADR 0029](adr/0029-setup-asks-work-eligibility.md)) block finishing, and optional imported suggestions never do. An import opens setup on the first step that still needs the person, never on a step whose only item is an optional suggestion. Finishing lands on Find jobs. Guided setup Basics and Profile › Basics render one shared field list — same fields, same order, same labels — with the location shown on resumes derived from city, region, and country rather than typed into a fourth field. The footer's action cluster is always the rightmost item on the footer's first row at every step, and while required items are outstanding `Save and continue` is a secondary action rather than the loudest control on the step. The stepper reports imported suggestions as "n suggested" rather than "n to review", so only work that actually gates finishing is described as outstanding. Success feedback is one auto-dismissing toast; errors stay on the route. A workspace that has not started setup opens guided setup directly instead of Home, and setup carries its own "Back to Home" control.
- Resume import recognizes every common bullet glyph (● • ▪ ◦ ‣ – — \* -), including glyphs joined mid-line, so role bullets become achievements instead of one paragraph; target roles are seeded from the headline plus recent titles. A multi-stage import that finalizes against a moved profile revision re-reconciles once and stays `applied`/`review_ready`; `failed` is reserved for extraction failures, and the Profile resume strip derives label and tone from the same source.
- Find jobs is the results page. The search bar above the results holds an optional focus note for one run, `Recent only`, a source picker (only when more than one source is enabled), a `Roles, places & sources` link that opens the read-only setup summary in place without a route change or a tab strip, and one `Search now` at its right end. The browser is named there only when it needs the person (sign-in or blocked); a search opens it itself. A workspace with no results opens that editor; the first saved results close it once. Find jobs never gates Search on the dedicated browser being open: the discovery run opens or attaches it. Only an offline catalog runtime or a genuinely blocked session blocks, and the visible CTA matches that blocker. Result rows show a recommendation badge only when it differs from the default review state and name the source once. The results header prints one plain count of the rows on the list (`9 jobs`, or `3 of 9 jobs` while a search or filter narrows it); the banded accounting belongs to the finished search's banner and to the dividers in the list. The sidebar badge counts the leading band plus the title-only band, while weaker matches and clear mismatches are one pool behind a single `Show weaker matches (n)` toggle whose accessible name is exactly its visible label; under `Cast a wide net` the list opens with that pool shown. Band headings say their own verdict (`Weaker matches (1)`, `Clear mismatches (1)`, `Matches your role, not yet scored (13)`), and a heading counts its whole band rather than the slice on the current page, so it equals the toggle’s count on every page. Sorting is one select whose options carry their direction (`Best match`, `Newest first`, `Company A to Z`); there is no density switch. Filters offer only facets with more than one value among the current results. A remote listing is not penalized against a preferred city when remote is a preferred work mode, unless `Count remote jobs as any location` is off; then a remote listing counts as a location match only when it names a saved place. The Job details pane shows the job before the reasoning — listing text, salary or "not stated", location and work mode, then one "why it fits" line — with the fit breakdown behind a `How this was scored` disclosure and the provenance (found on, original URL, application route, ATS, keywords, diagnostics, timeline) behind one `Source details` disclosure; a dimension that knows nothing is dropped rather than printed as an UNKNOWN card. Its footer offers `Open listing`, which opens the original page in the Job Finder browser, beside `Not interested` and `Copy link`. At desktop widths the results list and the inspector each own their own scrolling instead of growing the page. Below that breakpoint the list has no scroller of its own, so its scroll-bottom padding is not applied and a short result list leaves no empty strip under the last row.
- the Find jobs inspector never instructs the user to open a listing the app cannot open. When the listing text was not captured the inspector says so, and `Open listing` opens the page in the Job Finder browser; `Open listing` and `Copy link` stay visible even while the `Not interested` form is open. Every saved search criterion — roles, locations, work modes, sources — carries its own labelled edit control rather than only the empty ones, and the one `Roles, places & sources` control reports whether that summary is expanded. While a run is going, the elapsed seconds and the live kept-count appear beside the `Search now` control where the search was started, not only inside the separate activity panel.
- Shortlisted is three steps per job, in the order the work happens (ADR 0026): the resume level, one `Next step` block (a state line, one natural-width primary action, and one sentence saying what Apply does in the mode chosen in Settings), then the resume once one exists, then the job facts with the fit breakdown behind a `How this was scored` disclosure. There is no tab strip, no empty resume tab, no readiness facts, no checklist, and no batch curation. The only other per-job actions are two quiet links, `Open the listing` and `Remove from shortlist`. When two or more jobs are listed, one row above them offers `Create N missing resumes` and `Apply to all N ready jobs`. The shortlist column and the job column each own their own scrolling, so reading a long resume never scrolls away the job title or its state. A one-job list carries no search field, density switch, or all-jobs row. Pressing Apply goes to Applications at once with that job selected; until the run has written its record the list stays usable and carries one status line saying the application is starting, and a job with several records resolves to its newest one.
- Tailored drafts carry structured generation provenance (`ai`, or deterministic with a reason: no provider, provider failed, provider timeout, output unverified, forced). Resume Studio states that reason scoped to the _first_ draft ("The first draft came from the built-in generator because…"), and the reason and its detail survive every later save, patch, and export instead of degrading to a generic line. Draft origin and accepted assistant edits are one statement rather than two stacked notes that read as a contradiction: the first-draft sentence comes first, then "N assistant edits have been applied since, and the changed lines are marked in the preview", then the review reminder, with the Undo that restores the pre-edit wording on the same row. When the model wrote the first draft, only the accepted-edit sentence is shown. Deterministic compaction keeps whole sentences, drops truncated duplicates, splits legacy inline-bullet summaries into bullets at render time, keeps more job-relevant grounded skills visible, gives the most recent detailed role the widest budget of its own saved achievements, and repairs dotted technology-token spacing ("ASP .NET Core" -> "ASP.NET Core") without changing any claim.
- the separate browser window Job Finder drives has one name in every user-facing string, `the Job Finder browser`, and three actions with one name each: `Open the Job Finder browser` focuses that window on the paused application, `Reopen the Job Finder browser` is the same control demoted to secondary once the hand-off has happened, and `Check whether this step is done` confirms the user finished the step and came back. A sign-in or security check on the kept application page has no check press: Job Finder watches that exact page and carries on by itself once the wall is gone, and a file question carries on by itself once the file is added or restored in Profile › Files. The confirm action never renames itself; a running check is a pending state on the same control and a failed check is reported beside the row rather than by renaming the button. Pressing the primary hand-off action produces a visible state change: the open action drops to secondary and the confirm action is promoted to primary in its place. Applications owns the confirm action and `Needs you` uses the same verb.
- Apply opens no confirmation dialog: the apply mode is a Settings choice and screenshot checkpoints stay off unless turned on (ADR 0024).
- Each application's detail pane answers "did I apply?" with its state badge: `Applied` only when the employer's page confirmed receipt or the person recorded it, plus a `Not submitted` pill beside the title when a run reached a send control without sending.
- Applications keeps one box metric for every control in its recovery row, renders the Next step instruction at body size and prints it once, and moves convenience destinations below the recovery actions while an application is waiting on the user so the action row is inside the first viewport at the minimum supported size. A check reports itself in place beside the control that started it instead of through a top-of-screen banner; the latest automatic run appears only while it still needs attention; and the stacked disclosures are named for what they open (`Run details and history`, `More about this application`, `N earlier preparation runs`), each painting a rotating chevron and an underline so the affordance never depends on colour alone. The tracker's table/board/calendar switcher appears only with two or more records, and tracker settings save through the same control and the same four states as every other settings section. The Applications list and tracker panel titles render at the published heading scale rather than as bold uppercase primary-coloured type heavier than the page's own title, the detail pane uses one eyebrow label size rather than two unrelated ones, and the empty state's `Open Shortlisted` and `Find jobs` actions sit inside the empty-state box instead of stranded beneath it.
- Applications distinguishes an autosave pause ("The job site tried to save a field automatically…") from real field conflicts. The Next step callout owns that whole sentence, so the fact strip no longer relabels its two halves. `Open the Job Finder browser` opens the paused page, and `Check whether this step is done` beside it runs the exact same verification Needs you runs, so the hand-off loop starts and ends on one page. Run/checkpoint/artifact diagnostics collapse under "Technical details" and show only counts that stand for something the user can open. Home counts a source whose latest run completed as healthy.
- First-use Profile setup offers Light edit, Balanced rewrite, and Strong rewrite as tailoring defaults. Strong rewrite can substantially rewrite, combine, or elaborate only supported experience; every generated line remains reviewable, and Job Finder does not invent facts or numbers, auto-approve, or submit applications.

- resume import and profile editing with guided setup and the Assistant; each new import saves a private working copy and records the SHA-256 of those saved bytes. The first-run privacy explanation distinguishes the local working copy from optional configured-model analysis, and setup never implies that model processing is purely local. Import reports all four of its stages every time, with a determinate `Step n of 4`, a progress track, and the longest stage's typical cost stated from the moment it starts; a full import still runs in the foreground and still takes roughly half a minute, and it says so rather than appearing stalled. An import no longer freezes the guided-setup step editor: the user keeps typing into their own draft while it finishes and only saving is paused, with the footer stating the reason, so a late import response still cannot overwrite a concurrent draft. Existing legacy source references are migrated into app-owned storage when their bytes remain trustworthy; missing, unreadable, or changed legacy files show a replace-resume recovery path without discarding extracted profile details and cannot appear application-ready. Extraction retains every grounded role and bullet, derives work mode only from candidate evidence, keeps skills role-specific, and supplements sparse provider output with deterministic grounded evidence instead of silently dropping supported history. Re-importing unchanged app-owned bytes can reuse local analysis only when parser, provider/model, prompt, schema, reconciliation policy, and candidate-context fingerprints all match; refresh actions intentionally recompute because they do not reread and re-hash source bytes. In the profile editor, a half-filled project, language, proof, or custom-answer row blocks saving with a message that names the row instead of being dropped silently, fully empty rows stay optional, duplicate collapse applies only to import candidates (manual duplicates are never removed), the Main skills field stays independently authoritative while full-skill consumers derive their own unions from Main plus skill groups, and role-family fields accept comma- or newline-separated tokens. One router-level guard asks a single composed confirmation before any in-app navigation (link, push, or back/forward) that would lose unsaved profile, setup, or resume edits or abandon an in-progress or failed save; the confirmation is an app-owned accessible dialog that names each unsaved scope and offers Stay on this page or Leave without saving instead of a native browser prompt; hash-only fragment jumps stay exempt. Closing or quitting the whole window with unsaved work asks one app-owned confirmation instead of a native prompt, and an approved discard covers exactly that close — any later unsaved change asks again. When profile content changes in the background while the editor holds unsaved edits, untouched fields adopt the saved changes while edited fields keep the entered values under a notice to review the merged fields; if a safe merge is impossible, an explicit conflict keeps the unsaved edits and requires an explicit save or reload before continuing. A text stage that loses its configured-model call still finishes on the built-in deterministic reader, and Job Finder now says so instead of reporting a clean model run: the stage records why it degraded (a timeout or a provider error, with the provider's own summary), and the run and the profile carry one plain-language warning naming the affected part of the resume — for example that it could not use the AI model for the work history because the model did not answer in time, that it filled that part with its built-in text reader, and that those details are worth checking or the file worth importing again. That sentence appears with the import status it qualifies, in ordinary sentence case rather than as uppercase mono log output: Profile's resume panel prints it beside the imported file and its status, and guided setup's Import step prints it under `Import status` together with a countable hint derived from the run's own recorded stages (`2 of 3 AI stages used the built-in reader`), so a degraded import no longer reads as a clean one behind the word `Ready`. The raw provider detail stays in the run's warnings for diagnosis rather than in the user's notes. A timed-out call counts: it is the most common way this degrades. The degraded stage still produces a usable profile, and no claim in a generated resume gains support from it
- compensation keeps two deliberate truths: the typed search range guides matching and may contain only a minimum worth considering, while the reusable expected-salary answer is separate application text that can name a higher preferred range. Matching normalizes saved and listed amounts to an annual equivalent when their explicit currencies match, so monthly, hourly, and yearly wording are comparable without constraining how a job advertises pay. Unknown or different currencies remain neutral because the product does not guess exchange rates. Leaving the search maximum blank never caps or hides better-paying work, and application use still pauses for review. Deterministic Profile Copilot salary commands respect the same truths: they stage typed compensation operations for exactly the bounds the user expressed, keep stated currency (£/€/$/ISO) and pay period verbatim, inherit only an explicitly saved currency, ask a narrow question with no patch when low amounts lack a period ("2k") or when bounds contradict saved state instead of silently clearing or reinterpreting the other bound, route `salary expectations answer` phrasing to the stored application answer rather than structured compensation, and never convert between currencies or periods
- The profile chat is called the `Assistant`, matching Resume Studio, and is a floating panel rather than a docked rail: it keeps Profile's own geometry, tabs, and scroll ownership unchanged when it opens, keeps clearance from the save footer and the section tabs, and can be minimized to reveal anything it temporarily covers. It uses one schema-validated, review-first operation channel for all supported profile and search-preference edits, including scalar and list fields, structured records, removals, and review-item resolution. The runtime, not the model, owns proposal IDs, timestamps, and review state; chat cannot mark its own proposal applied. Explicit multi-field commands retain each field's own value, explicit `null` or empty-list clears are valid edits, and ambiguous clauses are omitted or clarified instead of borrowing a neighboring value. Apply, Reject, and revision-backed Undo remain separate user actions. The Assistant does not expose application submission or other external workflow authority.
- Profile owns its Save action the way guided setup does: the save footer is pinned chrome outside the scrolling content, so `Save changes`, the unsaved-changes statement, and the background-merge notice that the save resolves are painted inside the window at every supported size. Section tabs never truncate their own name; a finished section shows a check whose meaning is available to assistive technology, and only a section that still needs work spells out what it needs. The `Experience` tab is named `Work history`, matching guided setup and the card inside it, and `Proof bank` / `Add proof` are `Saved evidence` / `Add evidence`. A source's `Include in search` control is a plain checkbox that states On or Off rather than a pill shaped like the `Edit source` button beside it, and optional sections are opened by a control that says `Show` or `Hide`. Profile and every guided-setup step open with Save disabled and `No unsaved changes.`: the derived `currentLocation` line is no longer recomposed from its city/region/country parts while those parts are untouched, so an imported location carrying detail the parts do not can no longer make a profile permanently differ from its own saved record; editing any of the three parts still rebuilds the line, and clearing all three still clears it. The Basics helper text quotes that same stored line rather than a recomposed one, so it cannot announce a value the save would not write. The Profile footer, the guided-setup step footer, and the Settings save bar carry the save state as a dot plus colour as well as words, and a disabled Save is described by that visible line so a greyed control always has an attached, readable reason. The five section tabs sit on one row from 640px up instead of stacking into three rows below 1280px, which is what used to push a newly selected section's content below the fold at 1200x640 and 1024x720.
- browser-driven job discovery across configured targets; setup and Find jobs share one readiness rule requiring at least one enabled valid public HTTP(S) source. The full Profile has a dedicated Job sources tab for large libraries: it summarizes enabled/disabled/attention state, searches and filters the complete catalog, renders only 25 compact rows per page, and mounts the detailed check/guidance editor for one opened source at a time. Importing, suggesting, or storing a source does not enable it; the user must explicitly opt in, and only enabled sources run. Normal discovery targets up to 100 useful candidates across configured sources, while an explicit single-source run targets up to 50 and uses bounded result-pane scrolling and pagination before slower selective review; captured result cards prefer scoped title, company, and location fields so high-volume discovery does not trade away basic listing identity. Explicit target roles remain editable guidance, but are optional: when absent, discovery derives an inspectable search scope from saved target roles, experience titles, headline, skills, preferences, and exclusions instead of blocking on a vague title. Disabled search controls explain and link directly to the missing source owner. Guided setup includes the same basic source name, URL, and enabled-state editor used by the full Profile flow, and cannot complete while no runnable source exists. Independent public provider inventories begin concurrently, fast public-provider source checks avoid unnecessary browser work, and title/location/work-mode triage plus distinct-role budgets rank useful options against the active resume and explicit or profile-inferred scope. Public Lever boards use the matching US or EU provider endpoint from their hostname. Compact collision-safe known-job aliases, versioned fingerprints, freshness deadlines, and provider update timestamps skip unchanged enriched work early while changed/reactivated listings refresh; one shared identity resolver prioritizes provider/source-scoped posting IDs and normalized employer application URLs, treats exact title + company + location + absolute date only as a possible corroborating alias, and refuses ambiguous or conflicting legacy aliases instead of silently selecting or deleting an unrelated posting; later sources budget from distinct newly retained identities so duplicate-heavy early sources cannot consume their exploration share. Every source result explicitly reports inventory completeness as complete, partial, or unknown. Only a complete source inventory can mark a previously known exact listing inactive; partial or unknown observations preserve uncertainty. Interrupted or all-source failed discovery becomes an explicit failed record while safe results and history remain intact; partial multi-source success retains completed work and identifies failed sources for exact retry
- a fit percentage is a headline only when the evidence behind it is more than the listing title. A score earns its headline when at least one requirement was extracted, or role suitability settled to an exact match or a conflict, or preference alignment settled to aligned/mixed/conflict, or compensation was compared against a saved minimum, or evidence coverage reached moderate or high. When none of those holds — a card-only listing whose text was never captured — the inspector reads `Title match only` plus one sentence naming what is missing and what would change it, while a row inside that band carries the same verdict and sentence to assistive technology only — the band's own heading is the visible carrier, so the fact is stated once per band rather than repeated on every row. The number is neither discarded nor used to silently down-rank the listing: it moves inside `How this was scored`, beside the evidence it came from, as `Title-only estimate: n%`. An assessment not bound to the current profile and posting (a legacy row or an offline catalog seed) is stricter still — it reads `Fit not assessed` and carries no number anywhere. One helper is the single authority for that decision, so the row, the inspector, and the breakdown cannot disagree. Preference alignment counts as evidence only when it settled to `aligned` or `conflict`; a `mixed` verdict no longer earns a headline on its own. A requirement counts only when it was actually decided — supported, partial, missing, or conflict — and is not a saved-preference location or work-mode comparison, because the app emits those rows from the saved preference rather than from anything the listing said. Absence phrasing a board writes into a field (`not stated`, `not listed`, `not specified`, `not provided`, `not disclosed`, `unknown`, `n/a`, a dash, or empty — matched source-generically, with no board names) is unknown rather than a place: it can never produce a location conflict the app never observed, never becomes a requirement label, and never poses as captured listing evidence. The saved side follows the same rule: a preferred location that is only absence phrasing — an imported `Location not stated`, or a typed `N/A` — states no geographic constraint, so it is neither tokenised into a conflict against a real listing nor counted as a place the user chose and the listing met. A saved list holding both a placeholder and a real place is judged on the real place alone.
- career stage is a matching dimension. An opening explicitly reserved for entrants — early-careers, graduate, new-grad, internship, apprenticeship, entry-level, campus-hiring, or "class of 20XX" — is a clear mismatch against a profile whose saved evidence is senior, even when role family, skills, and every saved preference line up. It is never a peer tab beside Preparation. The configurable no-response rule defaults to 14 days. Preparation approval timeline entries describe opening/filling for preparation only, including legacy entries, and never imply submit approval. Externally observed stage changes use a blocking confirmation modal that isolates background focus, traps keyboard traversal, closes on Escape/backdrop cancel, and restores focus to its opener. Marking an application Applied or later is a manual tracking fact only; it never grants browser submission authority or invents a submission receipt.
- The global pause prevents new discovery, source-check, and application work and stops active owned work while local review and editing remain available. Campaign stop rules pause a preparation batch for configured login/signup blockers, changed or unexpected forms, unresolved human-answer or eligibility uncertainty, and an abnormal blocked/failed rate after its minimum sample.

The six phase-two slices below are implemented in the current checkout.

- Campaign rules are enabled/disabled `Must have`, `Prefer`, and `Never` rules over the evidence-backed job fields. Hard exclusions stay separate from ranking preferences; each rule shows its provenance and freshly measured remove/downgrade/unknown counts against the campaign's real retained jobs. The pre-search funnel is derived only from those real jobs — a campaign with no retained jobs yields a zeroed funnel instead of any invented estimate.
- Local schedules are enforced: run-now, daily, and selected-weekday runs respect time-zone-aware start times, pause windows, campaign limits, and the existing safe stop conditions; every finished run updates persisted run facts. A campaign digest persists new, changed, reactivated, inactive, known, skipped, and failed-source outcomes, and local in-app notifications cover strong new matches and blocked/failed campaign work. No external email or push integration exists.
- Outcome analytics record only explicit user-controlled outcomes on applications and slice them by campaign, source, job title, company, and resume strategy with real sample sizes, visible uncertainty, and conservative, inspectable, resettable suggestions that never change objective job facts. Recording rejects ambiguous identity: a job in multiple campaigns requires the campaign identity, and a job with multiple application records requires the application identity; the selected identities are persisted with the outcome. Recording `Applied` remains a local tracking fact and never creates submission evidence.
- Named role-family resume strategies carry a base resume, template, headline/skills/coverage policy, tailoring strength, evidence boundaries, campaign default, and a per-job selection with an inspectable reason. Automatic role-family recommendations and per-job selection are enforced. Strategy resolution passes the selected policy, including the base document and headline, skills, coverage, tailoring, and evidence boundaries, into résumé generation; reuse never approves, readies, or un-stales an artifact. A campaign default remains persisted when its strategy is disabled; the strategy screen keeps that disabled default visibly represented with an explicit clear action, while disabled strategies cannot be newly assigned.
- Search plans are optional reusable discovery settings for separating roles, sources, how much each run searches, rules, and progress; they do not configure or authorize application volume. They open from workspace search or from the link on Safeguards (neither the sidebar nor the `More` menu lists them), describe their volume in plain language, and keep Delete on its own row away from the safe actions. The current default plan is enough to start finding jobs. Home shows a `Search plan` selector once two plans exist, and Search plans switches plans too, because `Search now` always runs the current plan and a search reads its plan, settings, and preferences when it starts, so a saved edit is felt on the next search rather than a run in progress; the plan editor, the search-settings save, Settings, and Safeguards each say so at the moment of saving, and the plan editor offers `Search now with this plan`. Discovery filter, sort, and view selections persist per plan, so switching plans cannot leak selections between plans. Application preparation has a fixed limit of 10 unique employer jobs per run and a daily limit of begun employer applications that the person sets in Settings › Applying (default 20), across campaigns and legacy lineages. The dashboard separates exact usage from uncertain legacy capacity and shows the next local-midnight reset. Resume approaches are optional reusable role-family rules reached from Shortlisted job context: a job uses an explicitly chosen approach, and when the job has no explicit choice its search plan can name one enabled approach as a fallback recommendation; assignment and reuse never approve or make an artifact application-ready. Editing an approach shapes the next tailored draft only; each approach card says how many shortlisted jobs use it, and after an edit the page offers to re-tailor those jobs' unapproved drafts while approved resumes are left untouched.
- Company intelligence pages keep the complete company-linked saved-job collection, including openings hidden from the active discovery result set, plus applications, outcomes, contacts, notes, salary/offer evidence, source history, and preferences. Exact canonical names and user-approved merge aliases can own jobs; legacy aliases and domains cannot. Domains remain corroborating/conflicting research evidence, and existing jobs are not destructively rewritten around domain guesses. Listing activity stays distinct from application workflow state. A stale company URL shows `Company not found`, selects no substitute, and offers a route back to Companies. Conservative duplicate handling surfaces near matches as explicit merge-review candidates that require a user decision.
- High-volume safeguards add per-company/time-window application caps, simultaneous-application conflict checks, stale/closed/suspicious listing signals, abnormal-failure pauses, quality-review sampling, contradictory-answer protection, reversible dismissals, and explicit recovery guidance — all local tracking facts that never grant submission, credential, or account authority. Technical discovery/source-debug and application-terminal failures create idempotent safeguard and in-app notification evidence, while explicit user-owned blockers such as login, consent, CAPTCHA, MFA, or manual steps are excluded from the technical-failure sample. Contradictory grouped answers persist idempotent advisory safeguard evidence even when a reusable decision is rejected. Analysis concurrency remains saved policy rather than a runtime cap.
- `Not interested` can optionally hide the exact job and add an exact-normalized-employer exclusion in one atomic mutation after a preview. The reusable exclusion is offered only when company identity is unambiguous; domain evidence may corroborate identity but never creates a domain-wide exclusion. Reversal removes only the referenced employer exclusion and does not silently restore or rewrite unrelated job feedback.
- Application records are exact application lineages, not one mutable row inferred from a job. Starting another application creates a separate record; apply results, attempts, questions, answers, artifacts, replay checkpoints, consent, Needs you requests, campaign projections, and grouped-answer actions stay bound to that record. Manual answers preserve their exact run/job/result/question/application lineage and provenance; reusable Profile saving remains a separate explicit choice.
- CRM single-record and bulk stage changes merge against transaction-current application records. Bulk changes carry every visible expected revision, commit all selected records or none, retain manual tracker provenance, require confirmation before claiming externally observed stages, and keep failed selections available for explicit retry with a visible error. Company salary evidence must name its exact current job; offer evidence must also name the exact ApplicationRecord. Failed evidence saves retain the user's draft for correction instead of clearing it.

## Live Assistant

Current baseline:

- target-context setup from Job Finder records or direct user input
- rehearsal checks for transcript language, runnable audio/transcription paths, providers, screenshots, assistant responses, and retention defaults
- capture consent is capability-specific: a user can run system-audio-only, microphone-only, or screenshot-free sessions after accepting the core transmission, retention, and visible-surface disclosures
- a visible main-window conversation with explicit text sends, temporary PNG/JPEG/WebP attachments, screen-capture context, assistant replies, and a recent source-labeled transcript
- user-started microphone and meeting/system-audio transcription with queued transient chunks, local-command STT or configured cloud fallback, native-caption intake, and cue generation behind typed provider roles
- live sessions start with an empty transcript and no synthetic cue; standalone Whisper non-speech markers and short recorder-tail fragments are discarded instead of becoming coaching context
- post-session review, export, transcript annotations, delete, and explicit Job Finder follow-up actions
- starting an interview opens visible answer and transcript popup windows by default while the main conversation remains available; the answer popup is a compact interactive assistant with typed sends, pasted or selected image attachments, explicit screen-context capture, answer copy, and hide/reopen controls, while the transcript popup stays optimized for live source text with copy and hide/reopen controls
- popup workspace updates are event-driven rather than renderer reloads so live audio/transcript changes cannot erase an in-progress answer draft or pending image attachment; popup position and size persist across sessions
- personal-story requests without candidate evidence produce a bracketed STAR scaffold instead of invented employers, incidents, technology, timelines, metrics, or outcomes; screenshot-dependent questions use model-backed visual observations when available and otherwise disclose that visual analysis is unavailable instead of guessing from earlier transcript context

- active sessions expose a derived Session health summary for microphone/system-audio signal, transcription backlog and fallback, cue latency and fallback, popup visibility, and the latest recoverable failure. It uses existing local session state, preserves the session on failure, and never writes back to Job Finder automatically\r\n\r\nHard rule: capture, screenshots, attachments, advanced overlays, and model use must stay explicit, visible, auditable, and adapter-owned. See [ADR 0003](adr/0003-live-assistant-live-session-architecture.md) and [ADR 0008](adr/0008-visible-first-live-assistant.md).

## Product Defaults

- desktop shell: `Electron`
- renderer: `React`
- local persistence: `SQLite`; desktop startup enables rotating database-only recovery snapshots on graceful close plus a temporary pre-reset snapshot; a successful reset removes all managed snapshots and recovery quarantines. These snapshots do not include generated resumes, Candidate Assets, application documents, or browser-profile files
- browser runtime: managed sessions first
- AI: provider abstraction with separate chat, vision, STT, and embedding roles
- configured generative routing uses OpenCode Go: `muse-spark-1.3-contributor` through Responses with requested `xhigh` reasoning for text, tool, and image work, and `deepseek-v4.1-flash` through Chat Completions with `high` reasoning for aggressive resume tailoring only. Audio transcription remains local Whisper or an explicit audio-capable model. See ADR 0019 for routing and ADR 0009 for the contract-first agent boundary.
